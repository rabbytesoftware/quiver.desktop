## 1. Foundation: Stack Migration & Shared Building Blocks

### 1.1 Preact to React Migration

The current scaffold uses Preact with compat aliases. TanStack Router/Query have known issues with Preact's compat layer. We migrate to React proper.

**Changes:**
- Remove `preact` and `@preact/preset-vite` packages
- Install `react`, `react-dom`, and `@vitejs/plugin-react`
- Remove Preact compat aliases from `vite.config.ts` and `tsconfig.json`
- Update `src/main.tsx` entry point from Preact to React DOM
- Update `src/vite-env.d.ts` if needed
- Verify all shadcn/ui components work under React (they're originally React-native, so this should be seamless)

### 1.2 TanStack Router

Type-safe, file-based routing.

**Packages:** `@tanstack/react-router`, `@tanstack/react-router-devtools`, `@tanstack/router-plugin` (Vite plugin for file-based route generation)

**Route structure:**
```
src/
  routes/
    __root.tsx          # Root layout (shell, sidebar, etc.)
    index.tsx           # Home / dashboard
    quivers/
      index.tsx         # Quiver list
      $namespace.tsx    # Quiver detail (dynamic segment)
    arrows/
      index.tsx         # Arrow list
      $namespace.tsx    # Arrow detail (dynamic segment)
  routeTree.gen.ts      # Auto-generated by router plugin
```

The router plugin watches `src/routes/` and generates `routeTree.gen.ts` automatically. Routes are type-safe — link params and search params are validated at compile time.

**Root layout (`__root.tsx`):** Provides the app shell. For now, a minimal layout with an `<Outlet />`. The actual shell UI (sidebar, nav) comes in later stories.

### 1.3 TanStack Query

Server state management for all REST API communication.

**Packages:** `@tanstack/react-query`, `@tanstack/react-query-devtools`

**Setup:**
- `QueryClientProvider` wraps the app in `src/main.tsx`
- Default config: `staleTime: 30_000`, `retry: 1` (sensible defaults, tunable later)
- Query keys follow a factory pattern for consistency

**Query key factory (src/lib/api/query-keys.ts):**
```ts
export const arrowKeys = {
  all: ['arrows'] as const,
  lists: () => [...arrowKeys.all, 'list'] as const,
  detail: (namespace: string) => [...arrowKeys.all, 'detail', namespace] as const,
}

export const quiverKeys = {
  all: ['quivers'] as const,
  lists: () => [...quiverKeys.all, 'list'] as const,
  detail: (namespace: string) => [...quiverKeys.all, 'detail', namespace] as const,
}
```

### 1.4 Tauri v2 Sidecar Plugin

Configures Tauri to spawn the `quiver` daemon as a sidecar process.

**Rust side:**
- Add `tauri-plugin-shell` to `Cargo.toml`
- Register the plugin in `src-tauri/src/lib.rs`
- Configure sidecar in `tauri.conf.json` under `bundle.externalBin`

**Sidecar binary naming:** Tauri expects binaries in `src-tauri/binaries/` named with the target triple:
```
src-tauri/binaries/
  quiver-x86_64-unknown-linux-gnu
  quiver-aarch64-apple-darwin
  quiver-x86_64-apple-darwin
  quiver-x86_64-pc-windows-msvc.exe
```

For local development, the developer places their platform's binary manually. CI/release workflows fetch it from quiver.core releases.

**Frontend side:**
- `@tauri-apps/plugin-shell` npm package for invoking the sidecar from the frontend
- Sidecar management module (`src/lib/sidecar.ts`) that spawns the daemon on app start and kills it on exit

**Capabilities:** Add `shell:allow-spawn`, `shell:allow-kill` to `src-tauri/capabilities/default.json`.

### 1.5 Folder/Module Structure

```
src/
  components/
    ui/                 # shadcn/ui primitives (existing)
  lib/
    api/
      client.ts         # fetch wrapper pointing at localhost:{port}
      query-keys.ts     # TanStack Query key factories
      types.ts          # API response envelope types
    sidecar.ts          # Daemon spawn/kill via Tauri shell plugin
    utils.ts            # Existing utility (cn helper)
  routes/
    __root.tsx
    index.tsx
    quivers/
      index.tsx
      $namespace.tsx
    arrows/
      index.tsx
      $namespace.tsx
  main.tsx              # App entry: React DOM, QueryClient, Router
  routeTree.gen.ts      # Auto-generated
```

### 1.6 API Response Envelope Types

Typed to match quiver.core's contract.

**`src/lib/api/types.ts`:**
```ts
/** Standard envelope for all quiver.core responses */
export interface ApiResponse<T = unknown> {
  success: boolean
  error: string | null
  data?: T
}

/** Mutation responses return namespace instead of data */
export interface ApiMutationResponse {
  success: boolean
  error: string | null
  namespace: string
}
```

## 2. CI Workflow (`ci.yml`)

Triggered on PRs to `master` and `develop`. Mirrors quiver.core's CI structure but adapted for a Tauri (Rust + TypeScript) project without heavy testing.

### 2.1 Jobs

```
draft-reminder (ubuntu, draft PRs only)
validate-branch (ubuntu)
  ├── code-quality-frontend (ubuntu) — format, lint, types
  ├── code-quality-rust (ubuntu) — fmt, clippy, audit
  ├── build-frontend (ubuntu) — bun run build, verify dist/
  └── build-tauri (ubuntu) — cargo build --release, verify binary
```

**`draft-reminder`:** Comments on draft PRs reminding to run `make pr-checks`. Skips all other CI on drafts.

**`validate-branch`:** Enforces branching model identical to quiver.core:
- `enhancement/*`, `feature/*`, `fix/*`, `refactor/*`, `dependabot/*` → `develop`
- `hotfix/*` → `master`
- `release/*` → `master` (must branch from latest `develop`)
- Blocks CI on drafts.

**`code-quality-frontend`:** Bun install, `prettier --check`, `eslint`, `tsc --noEmit`.

**`code-quality-rust`:** System deps (webkit2gtk etc.), Rust toolchain, `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo audit`.

**`build-frontend`:** `bun run build`, verify `dist/` exists.

**`build-tauri`:** `cargo build --release` in `src-tauri/`, verify binary output. No sidecar needed — this is a compilation check only.

### 2.2 Environment

```yaml
env:
  RUST_VERSION: '1.85'
  BUN_VERSION: 'latest'
```

### 2.3 Caching

- Bun: `~/.bun/install/cache` + `node_modules`, keyed on `bun.lock`
- Cargo: `~/.cargo/{bin,registry,git}` + `src-tauri/target/`, keyed on `Cargo.lock`

## 3. Release Workflow (`release.yml`)

### 3.1 Versioning Scheme

Quiver uses **`YY.MM.XX`** format:
- `YY` = two-digit year
- `MM` = two-digit month
- `XX` = incrementing release number within that month

Examples: `v26.04.01`, `v26.04.02`, `v26.05.01`

Release candidates append `-rc.N`: `v26.04.03-rc.1`

### 3.2 Release Flow

```
release/YYYY-MM-DD ──PR──> master
    │
    ├─ CI runs (ci.yml)
    ├─ CI passes → release.yml fires
    │   ├─ Compute version: find last vYY.MM.XX tag, increment XX
    │   ├─ Build RC on matrix (ubuntu, macos, windows)
    │   │   ├─ Fetch quiver sidecar from quiver.core release (version input)
    │   │   ├─ Place in src-tauri/binaries/
    │   │   ├─ bun install && bun run build
    │   │   └─ cargo tauri build → native installer
    │   └─ Upload all installers to draft GitHub Release as vYY.MM.XX-rc.1
    │
    └─ PR merges to master
        │
        └─ merge-to-master.yml fires
            ├─ Create backport/YYYY-MM-DD-vYY.MM.XX branch from master
            ├─ Open PR: backport → develop
            ├─ Compute final version (strip -rc.N from latest RC tag)
            ├─ Build final release on matrix (ubuntu, macos, windows)
            │   └─ Uses shared .github/actions/build-tauri composite action
            └─ Publish GitHub Release vYY.MM.XX
```

### 3.3 Workflow Files

**`release.yml`** — Builds and publishes Tauri app bundles.

Triggers:
- `pull_request` on `master` from `release/*` branches, when CI passes (using `workflow_run` after `ci.yml` succeeds)
- `workflow_dispatch` with inputs: `version` (explicit version string), `quiver_version` (quiver.core release tag)

Jobs:
1. **`compute-version`** (ubuntu): If no explicit version input, scan tags matching `vYY.MM.*`, find highest XX, increment. Output the version string.
2. **`build-release`** (matrix: ubuntu, macos, windows): Fetch quiver sidecar → build frontend → `cargo tauri build` → upload installer artifacts.
3. **`publish-release`** (ubuntu, needs build-release): Collect all platform artifacts, create GitHub Release (draft for RC, published for final).

**`merge-to-master.yml`** — Handles post-merge automation.

Trigger: `push` to `master` (fires when release PR merges).

Jobs:
1. **`backport`** (ubuntu):
   - Create `backport/YYYY-MM-DD-vYY.MM.XX` branch from master
   - Open PR to develop using `gh pr create`
2. **`final-release`** (matrix: ubuntu, macos, windows):
   - Compute final version from the latest RC tag (strip `-rc.N` suffix)
   - Read `quiver_version` from the RC release metadata or a pinned config file
   - Fetch quiver sidecar → build frontend → `cargo tauri build` → upload installers
   - Create published GitHub Release (not draft)

**Token note:** `GITHUB_TOKEN` cannot trigger workflows in other workflow files (GitHub's loop protection). So `merge-to-master.yml` runs the final release build directly rather than dispatching to `release.yml`. This avoids needing a PAT or GitHub App. The trade-off is some build logic duplication between `release.yml` and `merge-to-master.yml`, which we mitigate by extracting shared steps into a reusable composite action (`.github/actions/build-tauri/action.yml`).

### 3.4 Sidecar Fetch Logic

Each matrix runner maps its platform to the quiver binary name:

| Runner | Quiver Binary | Tauri Target Triple |
|---|---|---|
| `ubuntu-latest` | `quiver-linux-amd64` | `x86_64-unknown-linux-gnu` |
| `macos-latest` | `quiver-darwin-arm64` | `aarch64-apple-darwin` |
| `windows-latest` | `quiver-windows-amd64.exe` | `x86_64-pc-windows-msvc` |

Downloaded via `gh release download` from `rabbytesoftware/quiver` at the specified `quiver_version` tag, then renamed to Tauri's expected `quiver-{target_triple}` format in `src-tauri/binaries/`.

### 3.5 Version Computation Logic

```bash
# Get current year and month
YY=$(date +%y)
MM=$(date +%m)

# Find latest tag matching this month
LATEST=$(git tag --list "v${YY}.${MM}.*" --sort=-v:refname | head -1)

if [ -z "$LATEST" ]; then
  # First release this month
  VERSION="v${YY}.${MM}.01"
else
  # Increment XX (strip -rc.N suffix if present)
  BASE=$(echo "$LATEST" | sed 's/-rc\..*//')
  XX=$(echo "$BASE" | awk -F. '{print $3}')
  NEXT=$(printf "%02d" $((10#$XX + 1)))
  VERSION="v${YY}.${MM}.${NEXT}"
fi
```
